# Additional BMFF Hash Exclusions

`builder.bmff_hash_extra_exclusions` adds exclusion descriptors to BMFF hash
assertions generated by the SDK. Callers can configure the exclusion policy
while retaining automatic hard-binding construction, including hashing,
Merkle generation, and placeholder handling. It defaults to an empty list.
Required and default exclusions remain in place; exact duplicates are not added twice.
The JSON/TOML settings travel through the existing `Context`, including from
C and Python callers.

```json
{
  "builder": {
    "bmff_hash_extra_exclusions": [{"xpath": "/sidx"}]
  }
}
```

Descriptors support `xpath`, `length`, `data`, `subset`, `version`, `flags`,
and `exact`. This setting accepts absolute paths composed of four-character
box names, without wildcards or occurrence indices. Settings loading checks
descriptor structure and subset arithmetic, not the semantic safety of
excluding the selected content. For example, excluding essential media or
decoding metadata can undermine the intended hard binding.

The setting applies to automatic file hashing, `mdat` Merkle hashing,
fragmented signing, and BMFF placeholders. One assertion list covers
initialization and media hashes: `/sidx` excludes every matching root-level
index, including one in the initialization region. This proposal does not
add automatic single-file fragment Merkle signing or rendition-ladder support.

Pre-existing assertions must already contain every requested exact descriptor.
This check also applies to embeddable signing and assertions reused across
renditions. The SDK does not retrofit exclusions onto a previously computed
hash. Generated placeholders already contain the requested descriptors.
BMFF update manifests reject nonempty requests; other asset formats are not
affected. These settings checks occur before signing or writing media outputs.

## Segment-Local SIDX

With the current single-file fragmented binding, a segment-local `sidx`
before the first `moof` enters `initHash`; later indexes enter the preceding
leaf. For segments containing `sidx + Merkle UUID + moof + mdat`, excluding
`/sidx` at signing allows each segment to be verified as delivered, using its
starting offset in the original single-file signed asset. The Merkle UUID is
already excluded by the required C2PA exclusion. Additional prefix boxes,
such as `styp`, remain subject to their own hash coverage.

[specs-core#2642](https://github.com/c2pa-org/specs-core/issues/2642) proposes
preserving associated segment prefixes within coherent authentication units.
Such a change could remove the need for this SIDX workaround. Generic
exclusion configuration remains useful for other explicitly selected
exclusion policies. The single-file signing and original-offset verification
capabilities needed for this use case are separate from this setting's
integration into the existing upstream signing paths.

## Index Integrity

Excluding `/sidx` leaves the media sample bytes and retained timing fields
authenticated. An altered index can affect fetching, seeking, presentation
completeness, and demuxed timing. For example,
[FFmpeg 6.1.1](https://github.com/FFmpeg/FFmpeg/blob/n6.1.1/libavformat/mov.c#L5340-L5359)
can derive fragment timestamps from `sidx.earliest_presentation_time` when
`use_tfdt=0`. Its default prefers `tfdt`, with SIDX also available as a
fallback. Consequently, unchanged authenticated timestamp fields can coexist
with changed demuxed timestamps.

Callers remain responsible for choosing an exclusion policy appropriate to
their media and consumers.

C2PA 2.4 permits additional BMFF exclusions and specifies the informational
`assertion.bmffHash.additionalExclusionsPresent` diagnostic. It does not
specifically endorse excluding `sidx`. The caller must assess the asset and
consumer profile rather than treating successful hashing as a semantic
compliance certification.
